# 階段 4:OOD Class Diagram(補行為) + Design Pattern 建議

## 目的

在階段 3 的結構圖上補上方法(behavior),並且在看到具體的「行為變異點」時,主動提出可能適用的 Design Pattern候選——但不是每次都要套,YAGNI 仍然優先,提出候選只是讓使用者能做知情的選擇。

## 補方法:先問「誰該負責這個邏輯」

對每一條在階段 1 Event Storming 裡出現的 Command / 業務規則,問:「這個動作,應該由哪個類別負責?」

判斷原則(Information Expert,GRASP 的核心概念之一):**擁有做這件事所需資料的那個類別,就該擁有這個方法**。例如「確認訂單」需要知道訂單目前狀態,這個方法就該長在 Order 上,不要放到一個外部的 Service 類別裡把 Order 當純資料袋。只有當一個行為明顯橫跨多個 Aggregate(例如「訂單確認後同時發送通知」)才考慮用 Application Service / Use Case 層去協調,而不是塞進單一 Entity。

## 主動提出 Design Pattern 建議:訊號 → 候選對照

在補方法的過程中,留意以下訊號,看到訊號就主動提出對應候選,附上理由,讓使用者確認要不要套用——**不要等使用者問才講**:

| 看到的訊號 | 候選 Pattern | 為什麼適合 |
|---|---|---|
| 同一動作依「類型」欄位分支出不同算法(if/switch on type) | Strategy | 把每種算法封裝成獨立類別,新增類型不用改既有程式碼 |
| 一個物件的建構需要多個可選步驟、順序敏感 | Builder | 把逐步組裝的邏輯抽離,建構過程可讀、可重用 |
| 物件的行為要依「狀態」改變,且狀態未來還會增加 | State | 把每個狀態的行為封裝成獨立類別,避免狀態機邏輯散落在一堆 if |
| 一個事件發生時,需要通知多個(而且未來可能更多)訂閱者 | Observer / Domain Event | 發布方不用知道有哪些訂閱者,新增訂閱者不用改發布方 |
| 建立一個複雜物件族的邏輯,應該跟使用它的地方分開 | Factory / Factory Method | 把「怎麼建立」的知識集中管理,呼叫端不用知道細節 |
| 需要相容一個外部系統/第三方 SDK 的介面差異 | Adapter | 把外部介面轉成內部慣用的介面,隔離技術細節 |
| 需要在不修改既有類別的前提下疊加新行為 | Decorator | 用組合取代繼承,行為可以自由疊加 |

## 怎麼提出建議(措辭原則)

看到訊號時,講清楚三件事,再讓使用者決定:

1. **具體的變異點是什麼**(不要只說「這裡適合用 XX Pattern」,要指出「你剛提到 <A> 未來還會有 <B>、<C> 兩種算法」)
2. **候選 Pattern 是什麼、為什麼適合**(對照上表)
3. **現在套 vs 先不套的取捨**——如果目前只看得到一種實作、使用者也不確定未來會不會變,提醒可以先用最簡單的寫法(例如直接 if/else 或單一方法),等真的出現第二種變化再重構成 Pattern,不用為了假設中的彈性預先套用。**只有在使用者確認未來變化是大概率會發生的,才建議現在就套。**

## 輸出格式

Class Diagram 補上方法簽名(沿用階段 3 的 mermaid code block,在每個 class 裡加 `+method(): ReturnType`)。

Pattern 建議整理成表格:

```
| 變異點 | 建議 Pattern | 理由 | 採用? |
|---|---|---|---|
| ... | ... | ... | 是 / 否 / 先不套,等出現第二種變化再說 |
```

## 停止條件

Class Diagram 的每個類別都有對應到階段 1 Command 的方法、使用者確認過每一條 Pattern 建議的「採用?」欄位,這階段才算完成。完成後回到 SKILL.md 的「完成後」章節收尾。
