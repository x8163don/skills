# 階段 2:Domain Analysis(Aggregate / Entity / Value Object)

## 目的

把階段 1 的事件時間序,收斂成三種戰術型模式:Aggregate(一致性邊界)、Entity(有身分、生命週期會變化)、Value Object(不可變、由屬性定義)。這一步決定了之後 Class Diagram 要畫哪些類別,順序不能反過來——先有邊界才有結構。

## 三個判斷法則(拿來問使用者,不是自己套)

### 1. Aggregate 邊界:「一致性」測試

問使用者:「當 <某個事件> 發生時,哪些資料必須同時更新、不能有一個成功一個失敗?」

會被綁在一起回答的那組資料,就是同一個 Aggregate 的範圍。Aggregate 的核心規則是:**一個 Aggregate = 一個交易邊界 = 通常對應一個 Repository**。如果使用者的答案讓 Aggregate 範圍一直擴大(什麼都要綁在一起),追問:「如果先更新 A、晚一點才更新 B,業務上可以接受嗎?」——可以接受的話,B 應該是獨立的 Aggregate,用最終一致性(例如靠 Domain Event 通知)串接,而不是塞進同一個交易。

### 2. Entity 測試:「身分 + 生命週期」

問:「這個東西的生命週期或狀態會隨時間改變、而且系統需要一路追蹤它嗎?」

會的話是 Entity——需要一個穩定的識別碼(ID),即使屬性全部改變,只要 ID 一樣就是同一個東西。

### 3. Value Object 測試:「可替換性」

問:「如果換成另一個屬性完全相同的實例,業務上有差別嗎?」

沒差別的話是 Value Object——不需要 ID,由屬性值本身定義相等性,通常設計成不可變(immutable)。常見例子:金額、地址、日期範圍、Email。

## 該問的問題(依序)

1. 針對階段 1 時間序列中「感覺會一起變」的事件群,問:「這幾個事件發生時,哪些資料一定要同時變、不能有一個成功一個失敗?」——找出第一個 Aggregate 候選。
2. 對每個候選 Aggregate,問:「這個 Aggregate 裡面,哪個東西是最終要負責守住規則的?」——找 Aggregate Root(通常是使用者最先想到、最常被引用的那個)。
3. 對 Aggregate 內的每個成員,套用「Entity 測試」和「Value Object 測試」逐一問過。
4. 問:「這個 Aggregate 要保護的規則是什麼?就算换了任何操作路徑,這件事永遠不能違反。」——這是 Invariant(不變量),之後 OOD 階段的方法設計要圍繞它。
5. 全部 Aggregate 列完後,問:「這些 Aggregate 之間,有沒有需要互相參照的地方?」——Aggregate 之間互相參照,原則上只用對方的 ID 參照,不要直接持有物件引用(避免打破邊界),如果使用者的設計看起來想直接引用,提醒這點並確認是否真的需要。

## 輸出格式

每個 Aggregate 一個區塊:

```
### Aggregate: <名稱>
- Root: <Entity 名稱>
- 內含 Entity: <列出,若無則寫「無」>
- 內含 Value Object: <列出>
- 不變量: <這個 Aggregate 永遠要保證的規則>
```

## 常見誤區(訪談中主動提醒使用者)

- **把整個資料庫當一個 Aggregate**:如果使用者傾向把很多東西塞進同一個 Aggregate,用「一致性測試」的反問(可否接受非同步更新)幫忙拆分。
- **VO 誤判成 Entity**:如果使用者說「這個地址有自己的 ID」,追問「這個 ID 是業務上真的需要追蹤這個地址本身,還是只是資料庫自動產生的?」——資料庫自動產生的 ID 不代表業務上是 Entity。

## 停止條件

所有從階段 1 事件時間序推導出的資料,都被分類進某個 Aggregate/Entity/VO,且使用者確認每個 Aggregate 的不變量寫得出來、講得通,才算完成。
