# 詞彙表(Ubiquitous Language)維護

## 目的

DDD 的 Ubiquitous Language 是指:團隊(業務、PM、工程師)跟程式碼裡,對同一個概念要用同一個字。這份 `glossary.md` 就是把這個「同一個字」的定義寫下來、跨功能累積,避免這次建模叫「訂單」、下次建模叫「點餐單」,結果指的是同一個概念,程式碼裡卻出現兩套命名。

只收錄 **Aggregate / Entity / Value Object** 這三種領域物件的名稱,不收 Domain Event / Command(那些是動作描述,重複度高、價值低,收了只會讓詞彙表變得龐大難查)。

## 檔案位置

固定放在專案根目錄的 `glossary.md`(如果專案是 git repo,用 `git rev-parse --show-toplevel` 找到的 repo root;不是 git repo 就用使用者目前工作的專案根目錄)。不要因為這次在某個子資料夾或某個 OpenSpec change 目錄下工作,就在那裡另開一份——詞彙表只有一份,分散了就失去「共用」的意義。

## 什麼時候讀、什麼時候寫

- **讀**:在 SKILL.md 的開場詢問時讀一次(如果檔案存在)。目的是讓階段 1、階段 2 的訪談沿用已定案的詞彙,而不是先各自發明命名、事後才發現衝突。
- **寫**:只在階段 2(Domain Analysis)產出 Aggregate/Entity/VO 名稱之後,做一次比對與寫回,寫回動作在整個建模流程「完成後」才真正落到 `glossary.md`(草稿階段先記在 `domain-model.md` 的「詞彙表異動」小節,等使用者確認過整份建模結果沒問題,再一次寫回,避免使用者後來改名卻已經污染了共用詞彙表)。

## 比對邏輯:新詞 / 沿用 / 衝突

階段 2 每產出一個 Aggregate/Entity/VO 名稱,對照 `glossary.md` 現有條目:

1. **詞彙表裡沒有這個名稱** → 這是新詞,草稿記到「詞彙表異動 → 新增」。
2. **詞彙表裡有這個名稱,而且定義一致**(講的是同一個概念,即使措辭略有不同)→ 沿用既有定義,草稿記到「詞彙表異動 → 沿用既有」,不要重寫定義。
3. **詞彙表裡有這個名稱,但定義明顯不同**(同名不同義)→ **停下來問使用者**,不要自己判斷取哪個。問法:

   > 「`<名稱>` 在 `glossary.md` 裡已經定義成『<舊定義>』,但這次建模裡它的意思是『<新定義>』。這是同一個概念只是描述角度不同,還是其實是兩個不同的東西、需要換個名字區分?」

   使用者可能給四種答案,分別處理:
   - **其實是同一概念,定義寫得不夠好** → 更新 `glossary.md` 的定義(用新的、更準確的說法),草稿記到「詞彙表異動 → 衝突已處理」,註明新舊定義與原因。
   - **真的是兩個不同概念** → 這次建模改用新名稱(跟使用者一起想一個不會撞名的名字),`glossary.md` 舊條目不動,新名稱另開一條。
   - **這是合理的 Bounded Context 差異**——同一個詞在不同業務語境下本來就該有不同定義(DDD 裡的正常現象,例如「Customer」在銷售情境跟在客服情境所指涉的屬性、生命週期可能完全不同),不是誰的定義寫得不好,兩邊都該保留 → 不合併、不改名,改成幫兩個定義各自標注所屬的 Bounded Context(問使用者:「這兩個語境各自怎麼稱呼比較好?例如『銷售』『客服』」),詳見下面「同名多義:Bounded Context 標注」。
   - **不確定,先擱置** → 記在 `domain-model.md` 的 Hotspot,不寫回 `glossary.md`,提醒使用者之後要回來決定。

## 同名多義:Bounded Context 標注

大多數專案只有一個 Bounded Context,詞彙表預設不需要標注——只有在真的遇到「同名不同義,但兩邊都合理」的情況,才需要引入這個概念,不要在一開始就強迫使用者切分 Bounded Context,那會讓簡單專案平白變複雜。

遇到這種情況時:
1. 問使用者兩個語境各自的簡短名稱(例如「銷售」「客服」「訂單子系統」),不用是正式的架構詞彙,使用者順口能講出來的就好。
2. 把 `glossary.md` 裡舊的那一條,標題加上 `(Context: <舊語境名稱>)`;新的這一條另開一個區塊,標題用同樣的詞彙名稱,加上 `(Context: <新語境名稱>)`。兩條都保留,互不覆蓋。
3. 如果之後又出現第三個語境用到同一個詞,重複這個標注方式即可,不需要回頭幫前兩條做額外處理。

## glossary.md 格式

```markdown
# Glossary(Ubiquitous Language)

## <詞彙(中文)> / <English Term,如有>
<這個詞在本專案裡的定義,1-3 句話>
- 所屬 Aggregate: <名稱,或「無,獨立 VO」>
- 分類: Aggregate Root / Entity / Value Object
- 來源: <哪次建模引入的,例如「線上點餐-訂單流程」>
```

單一語境(絕大多數情況)下,每個詞彙一個 `##` 區塊,同一個詞只會有一份定義。發現同名重複區塊時,先套用上面的比對邏輯判斷是「衝突」還是「合理的 Bounded Context 差異」——只有後者才允許同一個詞出現多個區塊,而且必須各自標注 `(Context: <名稱>)` 才能並存,標題格式:

```markdown
## <詞彙> (Context: <語境名稱>)
```

沒有標注 Context 的區塊,代表這個詞在整個專案裡目前只有單一定義,不要沒事就加上 Context 標籤。

## 寫回時的注意事項

- 只新增或更新條目,不要因為這次建模用不到某個舊詞彙就刪除它——那個詞彙可能是別的功能在用。
- 寫回前,把這次「詞彙表異動」的完整清單念給使用者看過一次再落筆,尤其是「衝突已處理」的項目,因為這會改變其他功能沿用的定義,值得讓使用者多看一眼。
