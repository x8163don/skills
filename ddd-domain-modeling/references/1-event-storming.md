# 階段 1:Event Storming(簡化版)

## 目的

在還沒決定任何類別、任何資料庫欄位之前,先搞清楚「這個流程裡按時間順序發生了什麼事」。這是後面所有結構性決策(Aggregate 邊界、Class 屬性)的依據——邊界從「哪些事必須綁在一起發生」推導出來,不是憑空猜的。

簡化版只抓三種記號,不做完整 Big Picture Event Storming 的 Policy / Read Model / External System / Hotspot 全套記號:

- **Domain Event(領域事件)**:已經發生的事實,用過去式命名,例如「訂單已建立」「付款已完成」。
- **Command(命令)**:觸發事件的意圖動作,用祈使句命名,例如「建立訂單」「確認付款」。
- **Actor(角色)**:誰(或什麼)發出這個 Command——可能是使用者角色,也可能是排程器或外部系統。

## 該問的問題

不要自己猜流程,照這個順序問:

1. 「從頭到尾,這個流程按時間順序,有哪些「已經發生的事實」?」——先讓使用者用自己的話說一遍,不要急著拆成 Event/Command。
2. 針對使用者說的每一件事,追問:「這件事是被誰的什麼動作觸發的?」——收斂出 Command 和 Actor。
3. 「有沒有哪個事件不是人手動觸發的,而是排程或外部系統自動發生的?」——找出非人類 Actor(例如「每日結算排程」「金流服務回調」)。
4. 「這個流程裡,有沒有你自己也還不確定該怎麼處理的地方?」——如果有,先記下來當作待釐清的疑點,不要卡住訪談,留到後面階段或跟使用者另外確認。
5. 「這個流程從哪個事件開始,到哪個事件算結束?」——確認時間序列的頭尾完整,避免漏掉流程前段或後段。

## 停止條件(何時可以進到階段 2)

當時間序列表從觸發到結束是完整的、使用者確認「沒有漏掉的事件」,才算這階段完成。如果使用者中途說「這個之後再說」,把它記在 Hotspot 清單裡,不要為了走完流程就自己編一個答案。

## 輸出格式

寫成一張時間序表,Actor / Command / Event 三欄,由上到下照時間順序排列。同一個 Actor 連續觸發多個 Command 就重複列出 Actor 那一欄,保持一行一組。

疑點另外列一個小清單,格式:`⚠️ <疑點描述>`。

## 跟階段 2 的銜接

進入階段 2 之前,先看一次整張時間序表,問自己(不是問使用者):「哪些事件的資料看起來一定要同時變更、不能有一個成功一個失敗?」——這個問題的答案就是階段 2 要問使用者確認的第一個問題,先在心裡打個草稿,但正式判斷交給階段 2 的訪談,不要在這裡就下結論。
