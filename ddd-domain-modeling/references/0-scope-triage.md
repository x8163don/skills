# 階段 0:規模與既有素材評估(在階段 1 之前)

## 目的

不是每次都該逼使用者走完整四階段。這一步的工作是:先看看有沒有既有文件已經回答過某些問題,再評估這次變更的規模,然後把「我建議走完整流程 / 建議跳過某些階段」講清楚讓使用者確認——**不是自己默默判斷、悄悄跳過**。跳錯了、漏做了該做的分析,比多問一句話的成本高得多。

## 第一步:找既有素材,而且要看內容,不是看有沒有檔案

先找這幾類文件(依序):

1. 如果在 OpenSpec 工作流裡,找 `proposal.md`、`design.md`(通常在某個 change 目錄下,或使用者剛剛在討論的那份)
2. 專案裡其他常見的 design/architecture 文件,例如 `docs/architecture.md`、`ADR` 系列文件、README 裡的架構章節、或使用者提到的任何設計文件

找到之後**實際打開讀內容**,不要只因為檔案存在就假設它涵蓋這次的範圍。讀完問自己:「這份文件裡,有沒有已經清楚定義了這次要建模的 Aggregate/Entity/流程?」——沒有明確寫出來的,就當作沒有,不要腦補文件言外之意。

## 第二步:依「覆蓋程度」分三種情況,各自有對應建議

### 情況 A:完全沒有既有素材,或既有素材沒提到這次的範圍
建議走完整四階段(階段 1 → 4)。跟使用者說一句原因即可,例如:「沒找到既有的領域分析,我們從 Event Storming 開始。」

### 情況 B:既有素材已經涵蓋部分或全部
先跟使用者核對「這份文件裡寫的,現在還準嗎?」(文件可能過時)。核對後,提議跳過已經被回答、而且確認還準確的階段,直接從還沒回答的階段接續。例如:既有 `design.md` 已經清楚定義了 Order Aggregate 的邊界與不變量,這次只是要新增一個折扣相關的欄位——可以跳過階段 1(不用重新做一次 Event Storming),直接從階段 2 開始,只針對「這個新欄位算 Entity 還是 VO、要不要影響既有不變量」發問。

### 情況 C:沒有既有素材,但這次變更明顯範圍很小
如果使用者一開始的描述就顯示這只是「在既有 Aggregate 上加一個屬性」「調整一個既有規則的參數」之類、看不出會新增 Aggregate 邊界或新的業務流程,建議簡化路徑:跳過階段 1 的完整 Event Storming,直接問階段 2 的 Entity/VO 判斷問題(這個新東西该放進哪個既有 Aggregate、算 Entity 還是 VO),階段 3、4 只針對受影響的類別局部更新,不用重畫整份 Class Diagram。

判斷「範圍很小」的訊號:使用者的描述裡沒有出現新的 Actor、沒有提到新的跨系統流程、沒有提到需要新增的不變量。只要有一個訊號不成立,傾向情況 A(完整流程),因為漏掉一個该有的 Aggregate 邊界的代價,遠高於多做一輪訪談的時間成本。

## 第三步:一定要問使用者,不要自己決定

不管評估結果是 A、B、C 哪一種,講清楚兩件事再讓使用者拍板:
1. 「我看到的情況是 <A/B/C 的具體理由>」
2. 「我建議 <走完整流程 / 跳過階段 X / 從階段 Y 開始>,你覺得可以嗎?還是想從頭完整走一遍?」

使用者永遠可以選擇「還是走完整的」——這一步的目的是避免不必要的訪談負擔,不是替使用者做決定。

## 停止條件

使用者確認要走哪個路徑後,才正式進入階段 1(或依情況 B/C 直接進入階段 2 的簡化版問題),參照對應 reference 繼續。
